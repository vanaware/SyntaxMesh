# Versão única: `version.ts` gerado pelo buildit, `VERSION` no barril do pacote

**Status:** Aceito
**Data:** 2026-11-08
**Fase:** 24 (CLI) — política transversal a `core`, `cli` e `service-worker`

## Contexto

Antes desta decisão a versão do produto existia em quatro lugares que podiam
divergir sem que nada falhasse:

1. `packages/core/src/version.ts` (`export const VERSION = "0.0.2"`);
2. `AppConfig.version`, que sobrescrevia o valor em `initTj3Config`;
3. literais nos scripts Ruby de golden (`scripts/golden/ical.rb`,
   `html-xml.rb`) e nos goldens serializados (`PRODID`, comentário
   "generated by");
4. um literal próprio no `service-worker` (`"0.0.2-mtvrt8od"`).

O bump era manual e cada esquecimento aparecia como golden quebrado ou como
`--version` divergente do manifesto. Além disso, `@vanaware/buildit` já é a
ferramenta de build do repositório e **já define o formato do arquivo de
versão**: `scripts/esbuild.jsonc#versionPaths` aponta para
`packages/core/src/version.ts`, e o esbuild injeta `__APP_VERSION__` (lido do
`deno.jsonc` da raiz) durante o bundle.

Consequência estrutural: **a versão definitiva só existe depois do build**. No
fonte — e portanto em `deno test`, nos goldens e em `deno run` — o que existe é
a constante não injetada.

## Decisão

1. **`packages/core/src/version.ts` segue o template do buildit**, sem
   alterações: declara `__APP_VERSION__` e cai em `""` quando o bundle não
   substituiu a constante. O valor não é editado à mão nem sincronizado com
   manifesto nenhum.

2. **O barril do pacote publica a constante como `VERSION`**:
   `export { APP_VERSION as VERSION } from "./version.ts"` em `src/mod.ts`.
   `@vanaware/syntaxmesh` (`.` → `mod.ts`) passa a ser a única porta de entrada
   da versão para consumidores externos — `packages/cli` importa daí.

3. **Módulos internos do core importam o folha, não o barril.**
   `app-config.ts` e `tj3-config.ts` fazem `import { APP_VERSION as VERSION }
   from "./version.ts"`. Importar `./mod.ts` de dentro fecha ciclos de módulo
   (`app-config.ts` é dependência de quase todo o core, inclusive
   `sheets/sheet-handler-base.ts`) e produz
   `ReferenceError: Cannot access 'SheetHandlerBase' before initialization` em
   quatro arquivos de teste de sheets.

4. **`service-worker` consome o subcaminho `@vanaware/syntaxmesh/version`**
   (`exports["./version"]` = `./src/version.ts`), não o barril: o SW roda em
   bundle próprio e não deve arrastar micromark/vento/reports só para ler uma
   string. `src/utils/config.ts` reexporta como `APP_VERSION` para o resto do SW.

5. **Oracle Ruby lê o `deno.jsonc` da raiz.** `scripts/golden/ical.rb` e
   `html-xml.rb` extraem `"version"` do manifesto — a mesma fonte que o buildit
   consome — em vez de farejar `version.ts`.

6. **Nenhum teste fixa a versão.** `packages/cli/tests/version_test.ts` foi
   removido (comparava `package.json`, `deno.jsonc` e `VERSION`, três arquivos
   que o bump já move junto). O que resta é a **derivação**:
   `packages/core/tests/version_test.ts` prova
   `VERSION === APP_VERSION` e `AppConfig.version === VERSION`;
   `packages/cli/tests/cli_test.ts` prova `--version` = `SyntaxMesh ${VERSION}`.

7. **Goldens neutralizam a versão (`@@VER@@`).** `ical_golden_test.ts` e
   `html-xml_golden_test.ts` substituem o token no `PRODID` e no comentário
   "generated by" dos dois lados antes de comparar. O golden continua byte-exato
   no resto; só a parte que depende de um valor que **não existe em tempo de
   fonte** fica fora da conta.

## Alternativas rejeitadas

- **Manter um literal sincronizado em `version.ts`.** Duplica a decisão do
  buildit (`versionPaths` existe para gerar o arquivo) e recria o bump manual
  que a decisão elimina.
- **`app-config.ts` importando `./mod.ts`.** Foi a primeira tentativa: quebra
  quatro arquivos de teste de sheets por TDZ em ciclo de módulos. O barril é
  para consumidor externo, não para dentro do core.
- **`service-worker` importando o barril.** Arrastaria o core inteiro
  (micromark, vento, registro de reports) para o bundle do SW.
- **Goldens com a versão concreta.** Obriga regeneração a cada bump e faz um
  teste falhar por um motivo que não é o que ele mede.
- **Normalizar a versão em todos os goldens.** Só os dois artefatos que
  serializam `AppConfig.version` precisam; a normalização geral continuaria
  no-op de propósito.

## Consequências

### Positivas

- Bump de versão toca **um** arquivo (`deno.jsonc` da raiz) + o bundle.
- `--version`, banner, `Project.version`, `PRODID` e o comentário do HTML saem
  sempre do mesmo valor injetado.
- Nenhum teste quebra por número de versão.
- O `service-worker` deixa de ter uma versão paralela e passa a compartilhar a
  do core, sem custo de bundle.

### Negativas / Riscos

- Em `deno run`/`deno test` (sem build) `VERSION` é `""`: `--version` imprime
  `SyntaxMesh ` e o `PRODID` sai `SyntaxMesh //EN`. É o preço de não haver
  versão definitiva antes do bundle; os goldens já toleram os dois estados.
- `app-config.ts` e `tj3-config.ts` dependem de um detalhe de grafo de módulos
  (importar o folha). Um import do barril ali volta a quebrar sheets — a
  restrição está documentada em ambos os arquivos.

### Neutras / Observações

- `CORE_VERSION` foi removida: era só um alias de `VERSION` sem consumidor.
- O subcaminho `./version` é o único ponto de API do core pensado para bundle
  alheio; qualquer outro subcaminho continua proibido (ADR 034, import único
  pelo barril).
