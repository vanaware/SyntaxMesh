# Phase 25 — Temporal API Migration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the core's `Date`/`TjTime` temporal model with an explicit, corrected Temporal API while keeping `.tjp` syntax and the JSON `execute()` envelope stable.

**Architecture:** Migrate by vertical slices behind temporary internal adapters, then remove all legacy temporal contracts at phase closure. Native Temporal is selected when available; `@js-temporal/polyfill` is the deterministic fallback through one core adapter.

> **Execution note (2026-11-28):** F21 waves 1–2 and F22 were delivered early. Phase 25 is the next pending phase; affected goldens, snapshots, benchmarks, and bundle checks must be rerun after migration.

**Tech Stack:** Deno 2.9.8, TypeScript strict mode, Temporal API, `@js-temporal/polyfill`, `@std/testing/bdd`, `@std/assert`, existing TaskJuggler golden and benchmark harnesses.

**Spec:** `docs/syntaxmesh/fases/fase-25-temporal-api.md`

## Global Constraints

- Deno only for project tasks; no Node-specific APIs in core source.
- Deno >= 2.7; the verified workspace runtime is 2.9.8 with native Temporal.
- Native Temporal plus `@js-temporal/polyfill` fallback through `packages/core/src/time/temporal.ts` only.
- No domain module may import the polyfill directly or mutate `globalThis.Temporal`.
- `Instant` is canonical for absolute time; `ZonedDateTime` carries project timezone; `PlainDate`, `PlainTime`, and `Duration` own calendar, working-time, and effort concepts.
- Project timezone is explicit; when omitted it defaults deterministically to `UTC`. Host timezone access is forbidden.
- DST policy is `disambiguation: "compatible"` and `offset: "prefer"`.
- Corrected Temporal behavior is the only supported behavior for migrated methods.
- `TjArgumentError` has a stable owner outside `tj-time.ts` before the legacy facade is deleted.
- `TjTime` is removed from public exports and consumers at phase closure.
- `.tjp` syntax and JSON `execute()` field shapes remain unchanged; Temporal objects do not cross JSON boundaries.
- All new tests use `@std/testing/bdd` and `@std/assert`.
- Every production behavior change is TDD: failing test, minimal implementation, passing targeted test, type/lint/format check, evidence registration.
- Baseline, audit, ADR, documentation, and gate tasks use their objective evidence commands instead of a synthetic failing test.
- Legacy audits use executable patterns, not bare `Date` token searches; comments and enum names are classified separately.
- Wall-clock timestamps use injectable `Instant`; monotonic test deadlines use `performance.now()`.
- Do not commit unless the user explicitly requests it.
- Ruby `tj3` remains the legacy baseline; corrected temporal fixtures use explicit reviewed expectations and must not be regenerated from Ruby output.
- Bun is required for the approved runtime matrix. It was not installed in the planning environment; 25.0.3 stays blocked until Bun is available, and a missing runtime is never recorded as a pass.

## Execution Protocol

Each task row has a `Done` checkbox. A task is complete only when its verification
command passes and its evidence row is registered.

For production behavior tasks:

1. Write the failing BDD test or reviewed fixture change.
2. Run the task's targeted test command and confirm the expected failure.
3. Implement the smallest production change.
4. Re-run the targeted test and confirm it passes.
5. Run the listed type, lint, and format checks.
6. Add one evidence row with command, result, and affected files.
7. Mark `Done` as `[x]` and update progress counters.

For baseline, audit, ADR, documentation, and gate tasks:

1. Run the objective command or review listed in the task.
2. Record the output, counts, hashes, or reviewed diff in the evidence register.
3. Mark `Done` as `[x]` and update progress counters.

Commits remain optional and require an explicit user request.
